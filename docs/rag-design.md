# 音乐证据型 RAG 完整设计

状态：已实现人工维护、检索与引用链路，并通过隔离环境功能验收；真实音乐语料质量目标待维护者标注评测。更新日期：2026-11-03。

本文件替代原初步设计，按完整功能定义范围、契约和验收，不划分交付阶段。运行操作见 [维护说明](./rag-maintenance.md)，已验证结果与边界见 [验收记录](./rag-validation.md)。本文中的质量门槛仍为目标，不代表已在真实音乐语料上达标。

## 1. 产品定位与确定的边界

RAG 为现有统一音乐探索 Agent 提供可追溯、可更新、可撤回的音乐证据，支持歌曲/专辑分析、艺人探索、推荐解释与连续追问。

- 对外只保留统一 ReAct Agent，`search_knowledge` 是其自主选择的原子工具，不新增对外 RAG Agent，不强制每轮对话检索。
- 网络发现与 MusicBrainz 身份核验仍是新歌曲推荐和候选池构建的主链路；知识库只补充事实、语境及解释。知识库为空、无覆盖或故障不得阻断普通推荐。
- 当前知识库采用人工维护：维护者主动选择资料、导入、修订、审核和发布。系统辅助解析、去重、实体匹配建议、候选提取和向量化，人工维护不等于逐条手工录入。
- 自动发现、定时采集及从日常对话自动沉淀知识不属于当前实现范围，只预留接入契约。后续自动收集也只能产生候选资料，不得跳过审核发布。
- 当前仅建设维护者管理的公共音乐知识库，不开放普通用户个人文档库。对话、收藏、投票和个人偏好继续属于现有记忆系统，不自动变成公共知识。
- 不保存完整歌词、受限整篇文章、音频或能重建歌词的嵌入内容。公开材料只保留允许保存的必要摘要、短摘录及元数据。
- 用户最终回答的长度仍由问题、证据和研究投入决定。检索证据数量及预算不构成回答字数限制。

## 2. 当前实现与必须补齐的能力

已存在 ThemeCardKnowledgeStore、FastEmbed、Milvus、主题卡审核导入脚本和统一 Agent 的 `search_knowledge` 动作。静态代码检查发现：

1. 入库检查 LOCAL_CURATED + APPROVED，检索没有对应的强制过滤和权威状态回查。
2. KnowledgeSearchTool 的 `recording_ids` 未参与过滤，调用端还传入空列表，缺少完整音乐实体与版本约束。
3. 检索异常被转为 `[]`，无法区分无命中、模型故障和 Milvus 不可用。
4. 现有知识结果缺少可追溯的来源版本、支持短摘录及知识审核版本。
5. `conversation_graph.py` 将知识与 web_sources 分离，分析合法引用主要来自网络来源；本地证据没有进入完整的引用、覆盖判断和持久化闭环。
6. 现有 OutboxPublisher 使用固定 Agent 路由，不能直接将知识任务投入同一消费队列。
7. 尚缺权威知识表、版本生命周期、索引任务、撤回及对账机制。

历史规格记载的主题卡数量不能当成本机已有数据；必须检查导入文件、审核记录和实际索引。本地运行文档记录的 Milvus/MinIO 启动问题也必须在实施时重新验证。

## 3. 知识类型与来源准入

| 类型 | 内容 | 使用边界 |
| --- | --- | --- |
| FACT | 发行、合作、署名、版本关系等事实 | 必须绑定支持材料、规范实体及适用版本 |
| ATTRIBUTED_STATEMENT | 采访发言、媒体评价 | 保留发言人、评价主体及语境，不转写为无条件事实 |
| EDITORIAL_CONTEXT | 有来源的流派、音乐史和文化语境 | 标明来源及解释边界，不推导创作者意图 |
| THEME_CARD | 审核后的主题、情绪、场景、叙事与听感 | 仅支持解释性分析，不证明创作背景或制作署名 |

材料优先来自艺人/发行方公开说明、正式采访、可核实目录和有署名的音乐研究材料。来源类型只是判断线索，人工审核仍需核对具体正文是否支持表述。维护者原创观察须明确标为观察，不因审核而升级成创作者事实。

现有主题卡必须同时满足 `sourceType=LOCAL_CURATED`、`reviewStatus=APPROVED`、实体绑定和发布条件。EXPERIMENTAL_LYRIC_DERIVED 仅供离线实验，不能通过格式转换自动进入正式检索；主题卡不要求保留歌词原文作为支持材料。

同一采访的转载、摘要及翻译应记录同源关系，不算独立来源；来源存在冲突时保留冲突关系和适用范围，不以多数网页或向量分数决定真伪。

## 4. 架构与职责

```text
维护者：文件导入 / 指定网页 / 手动编辑
  → Java：来源版本、实体绑定、审核、发布与审计
  → MySQL 权威数据 + 同事务 Outbox
  → RabbitMQ 知识任务队列
  → Python 知识 Worker：辅助提取、向量化、索引维护
  → Milvus：可重建索引

用户消息 → 统一 ReAct Agent 自主选择 search_knowledge
  → 受约束的实体扩展 + 精确召回 / 向量召回
  → Java 批量权威核验
  → 统一证据集合 → 回答与条件式审校 → 持久化卡片和引用
```

Java 是唯一知识权威中心，管理权限、版本、审核、状态、审计和最终引用校验。Python 不直连 MySQL，只通过鉴权内部 API 读取证据与回报任务。Milvus 不决定资料是否有效。RabbitMQ 传递任务，MySQL 保存任务状态和恢复事实。知识 Worker 与 Agent Worker 独立部署及限流。

## 5. 人工维护与导入流程

### 5.1 当前支持的输入

- JSONL：结构化事实、主题卡及来源元数据；逐条校验并返回错误。
- Markdown/TXT：文件正文与来源元数据，辅助提取候选知识。
- 维护者指定的公开网页 URL：只读取维护者选定的页面，不自动爬取整站。
- 维护端直接创建和编辑条目。

不建设通用 PDF/OCR 管线；需要此类资料时由维护者整理为支持格式并保留准确定位。链接读取必须限制协议、端口、响应体、超时和重定向，并在每次重定向前重新执行 SSRF 检查；无法取得正文时明确失败，不以搜索摘要伪装精读。

### 5.2 完整操作链

资料登记 → 解析与去重 → 候选提取 → 实体确认 → 材料对照审核 → 发布 → 索引。

这是资料处理过程，不是约束用户 Agent 的固定工具顺序。

- 提取器只创建 DRAFT，不能执行审核、发布或直接写正式集合。
- 维护者确认摘要、出处、实体、版本范围、观点归因及允许的使用方式。
- 审核记录绑定内容摘要哈希和知识版本；内容、实体或材料改变后生成新版本并重新审核。
- 批量操作可部分成功，保留逐条结果与断点；重试不能重复创建相同版本。
- 文件指纹用于幂等辅助，不能代替稳定资料标识；不同发布者相同文本仍保留来源和转载关系。
- 外部文本作为资料数据处理，不执行其中的命令，不允许它改变系统提示、工具权限或审核规则。

### 5.3 后续自动收集的扩展点

定义统一 CandidateSubmission 输入契约，当前人工导入也使用它：

| 字段 | 含义 |
| --- | --- |
| submissionId / idempotencyKey | 提交及幂等标识，由服务端核验 |
| origin | MANUAL_FILE、MANUAL_URL、MANUAL_EDIT；预留 AUTOMATED_COLLECTOR |
| submittedBy / submittedAt | 可信调用身份和时间，由服务端填写 |
| sourceDescriptor | URL/资料标识、标题、发布者、语言和使用限制 |
| contentFingerprint | 内容指纹，用于重复检查 |
| candidateItems | 候选条目、实体建议、来源定位和必要短摘录 |
| collectorRunId / extractionVersion | 可空的采集运行标识和提取器版本 |

当前不部署自动采集器、不启用定时发现任务，也不开放 AUTOMATED_COLLECTOR 写入口。未来采集器只能以独立服务身份提交候选，由同一入口校验、去重并进入 DRAFT；没有审核发布权限。该预留不承诺未来允许自动审核，自动发布需要另行设计与明确授权。

日常 Agent 取得的网页可以作为当轮公开证据；当前不自动转存为长期知识。维护者可主动选择资料重新导入。即使未来增加“提交候选”能力，也不应把用户私人对话或偏好作为公开采集内容。

## 6. 权威数据模型

采用稳定条目 ID 与不可变内容版本。来源、知识版本和索引代次分别管理。

| 表 | 核心字段/责任 |
| --- | --- |
| knowledge_source | id、规范资料标识、当前来源版本、ACTIVE/RETRACTED 状态 |
| knowledge_source_revision | source_id、revision、标题、URL、发布者、材料类型、语言、发布/采集时间、指纹、同源标识、使用限制 |
| knowledge_entry | id、knowledge_type、当前发布版本、UNPUBLISHED/PUBLISHED/RETRACTED 状态、撤回原因 |
| knowledge_entry_revision | entry_id、revision、summary、受控谓词及归因、适用时间、内容哈希、审核状态、创建/审核记录 |
| knowledge_entry_entity | entry_revision_id、entity_type、内部 UUID、MBID、关系角色和适用范围 |
| knowledge_evidence_link | entry_revision_id、source_revision_id、短摘录、定位、SUPPORTS/CONTRADICTS/CONTEXT_ONLY 关系 |
| knowledge_ingestion_job | 批次、输入来源、origin、幂等键、提取器版本、进度与逐条错误 |
| knowledge_index_job | 知识版本、索引代次、动作、状态、租约、重试、下次执行时间及脱敏错误 |
| knowledge_index_generation | 模型文件版本、维度、文档/查询模板、集合名、状态、切换记录 |
| knowledge_audit_event | 操作者、对象版本、动作、时间、理由及前后状态 |

约束与语义：

- `(source_id, revision)` 和 `(entry_id, revision)` 唯一；已发布版本不能原地改写。
- 一个条目版本可关联多份支持或冲突材料，不能只用单个 source_id 表达全部依据。
- 有效引用必须绑定知识版本、来源版本及支持关系，不能只存 URL。
- 短摘录保存足以核验表述的必要上下文，不以摘要自证摘要；无法保留时记录边界及人工核验依据。
- 同一条目最多一个当前发布版本；修改草稿不会自动撤销旧发布版本。发布新版本时原子替换发布指针，旧版本不再用于新回答。
- 审核状态为 DRAFT / IN_REVIEW / APPROVED / REJECTED；发布状态独立。APPROVED 不自动等于公开可检索。
- 普通撤回隐藏当前条目，保留审计；来源失效阻止相关材料继续使用。合规删除可按要求清除摘录和快照，保留必要的非正文审计。
- 来源页面内容改变时创建新来源版本；旧知识不能静默改绑新正文。新材料经审核后再发布对应知识版本。

## 7. 实体解析与版本范围

实体至少支持 ARTIST、RELEASE_GROUP、RELEASE、WORK 和 RECORDING。MBID 必须与实体类型一同使用；本地未覆盖的实体可用经过核验的规范标识关联，不要求为了导入而制造待推荐歌曲。

关联角色包括 SUBJECT、CREATOR、ALBUM_CONTEXT 和 RELATED_WORK。知识适用范围区分作品整体、发行、录音版本、艺人阶段和时间区间。

- STRICT：指定现场版、重录版或某次发行的署名时，只接受匹配范围的证据。
- RELATED_CONTEXT：背景研究可沿经过核验的关系扩展，如 Recording → Work / ReleaseGroup，保留扩展路径。
- 艺人背景不自动成为每首歌的创作事实；作品事实不自动证明某次录音的编曲、制作或混音事实。
- 同名、别名及跨语言名称通过现有实体解析机制确认；可靠解析失败时复用持久化澄清，不静默猜测。
- 没有实体条件的主题查询允许受控语义检索；涉及具体作品事实时必须在使用前确认对象。

## 8. 索引任务与一致性

### 8.1 写入及消费

发布、替换和撤回在同一 Java 事务中修改权威数据、创建索引任务并写 Outbox。将现有固定 Agent 路由改为受控事件类型映射，知识任务使用独立队列、死信和并发限制；不得改变既有 Agent Run 消费契约。

索引任务唯一键包含 `(entry_revision_id, generation, operation)`。Worker 领取租约，读取指定不可变版本，执行索引，向 Java 回报成功后再确认消费。写入成功而回报失败允许重试；幂等操作必须保持相同结果。过期租约不能回写新领取者的任务状态。

索引行主键采用规范化的 `entry_id + revision + generation` 字符串。不同内容版本使用不同主键，避免延迟 v1 UPSERT 覆盖 v2。DELETE 必须针对明确版本；不得以旧任务删除整个条目的所有新版本。

任务状态：PENDING → RUNNING → SUCCEEDED；失败进入 RETRY_WAIT，达到上限进入 DEAD；已无意义的未执行旧任务可标为 SUPERSEDED。重试使用有界退避，不做无限即时重新入队。

### 8.2 检索权威检查

Milvus 命中必须携带内容版本及索引代次，Java 批量检查：

1. 知识处于 PUBLISHED 且命中版本等于当前发布版本；
2. 该版本审核为 APPROVED，材料关系可用于当前知识类型；
3. 来源有效，且支持关系指向具体来源版本；
4. 实体、适用范围和访问权限满足本次请求。

旧向量不能按稳定 ID 换取新正文。被过滤结果可触发有界补召回，仍不足时明确返回覆盖边界。

撤回事务提交后，之后执行的权威检查拒绝该证据，向量删除可以异步。Java 在最终结果落库和开始交付前再次校验引用；如果生成期间失效，应让同一 Agent 修订受影响结论，不能只删掉引用而留下原事实。

已经开始发送的回答不能承诺追回。撤回后引用查询显示失效状态，历史回答保留当时依据或按删除要求清除受限材料，新回答不得继续沿用。

定时对账检查发布条目未索引、索引版本不匹配、过期向量、丢失任务、失败任务和源状态变化；任务重复、乱序、网络超时及 Worker 崩溃必须可恢复。

## 9. Milvus 集合、嵌入与升级

事实类与主题卡使用两个集合族：`isq_fact_evidence_g{n}`、`isq_theme_cards_g{n}`。一个请求固定索引代次及其模型，不跨代次混合距离。

索引字段包括版本化主键、entry_id、revision、generation、知识类型、主要实体、关联实体、语言、内容指纹和向量。实体多值过滤须在固定 Milvus/SDK 组合上验证，不能依赖未验证版本能力；需要时由 Java 先提供受控候选 ID 约束。

权威正文、来源和审核状态由 Java 返回，Milvus 中的冗余字段只用于过滤和召回，不能绕过回查。

- 复用 FastEmbed 和 BAAI/bge-small-zh-v1.5 作为基线，固定模型文件修订、依赖版本及服务端/客户端组合。
- 显式版本化文档模板、查询模板、向量维度、归一化和输入长度策略。
- 事实输入包含规范实体上下文、必要归因及原子知识；主题卡输入沿用无歌词的标题、艺人、主题和概述。
- 超长输入应返回编辑/拆分任务，不能静默丢弃关键限定条件。
- 不强制引入独立重排模型；由固定评测衡量是否需要。跨语言和别名表现必须单独评测。
- 小规模场景默认用 Strong 读取验证发布可见性；任何读取配置都保留权威核验。

模型升级：创建 BUILDING 代次 → 全量回填 → 同步发布增量 → 对账及固定评测 → 原子切换 ACTIVE。保留旧代次用于回退；回退前须确保它已追平期间的发布和撤回事件。每个请求读取一次代次配置，避免中途切换模型与集合。清理旧代次前确认无运行中任务依赖。

## 10. 检索契约与内部算法

请求示例：

```json
{
  "query": "这首歌的创作背景",
  "entities": [{"type": "RECORDING", "id": "规范实体标识"}],
  "entityScope": "RELATED_CONTEXT",
  "knowledgeTypes": ["FACT", "ATTRIBUTED_STATEMENT"],
  "limit": 6
}
```

权限、预算、代次和可信用户上下文由服务端提供，不能信任模型自报。

检索内部过程：

1. 从请求及已确认上下文恢复对象，计算允许扩展的实体集合。
2. 并行执行 Java 精确召回及 Milvus 向量召回；精确通道使用规范名称、别名、标题及受控谓词，不依赖未经验证的中文全文分词。
3. 每路默认召回 20 条，按知识版本去重，用应用层 RRF 融合；精确匹配、实体适用性、证据直接性作为受控排序信号。
4. 批量回查权威状态和证据正文，去除失效与错实体结果，控制重复及同源占比，但不因多样性规则丢掉唯一直接证据。
5. 默认返回最多 6 条；多对象比较按对象分配预算，覆盖不足时返回说明。必要补召回受总时限和次数约束。

状态定义：hit 表示有有效证据且通道正常；partial 表示有有效证据但部分通道不可用或对象覆盖不足；no_match 表示完整检索正常完成但没有合格证据；unavailable 表示无法完成权威核验，或检索降级后无有效结果且不能判断为无匹配。

Milvus 故障时可返回 Java 精确通道的有效证据并标 partial；Java 权威服务故障时不能直接返回未经核验的向量正文。记录脱敏原因码，不向用户暴露内部地址或原始异常。

cosine 相似度仅参与召回，不是事实正确率。阈值通过开发集标定，验收集独立保留；结果质量不能由命中数量代替。

## 11. 统一证据与 Agent 接入

检索响应使用统一 Evidence 对象；网络、目录关系和本地知识共享引用机制，保留 origin 和知识属性。

```json
{
  "status": "hit",
  "coverage": {"completeForRequestedEntities": true},
  "evidence": [{
    "ref": "E1",
    "origin": "KNOWLEDGE",
    "knowledgeType": "FACT",
    "statement": "由材料支持的具体表述",
    "entities": [{"type": "WORK", "id": "规范实体标识"}],
    "support": [{
      "sourceTitle": "采访标题",
      "sourceUrl": "https://example.org/interview",
      "sourceVersion": "来源版本",
      "locator": "创作背景段落",
      "excerpt": "允许保存的必要短摘录",
      "relation": "SUPPORTS"
    }],
    "boundary": "仅适用于作品原作背景"
  }]
}
```

还需携带发布者、材料属性、日期、原始/转载关系及适用范围。内部使用的知识版本、校验令牌、审计字段和分数不直接展示。维护者笔记没有公开 URL 时明确标为维护者整理，不虚构外部链接。

Agent 改造必须覆盖整个证据闭环：

- 从分离的 knowledge / web_sources 改为统一 evidence 注册表；ref 在同一 Run 中稳定，结果排序变化不能重新编号。多轮卡片引用通过持久化证据 ID 映射恢复。
- 更新 tool/skill 元数据，让 search_knowledge 支持已审核事实和解释材料。
- 合格本地事实可计入分析证据充分性；去除仅以“没有网络来源”判定无法分析的条件。
- 证据充分性按问题、材料直接性、版本及来源强度判断；遵守项目对事实密集研究的独立来源核验约束。转载不算独立来源，不足时继续研究或明确降低结论强度。
- 检索状态不改变 Supervisor 的自主权；它可继续搜索、精读、澄清或停止，不引入固定检索—写作 DAG。
- FACT、OBSERVATION、INTERPRETATION 和 LISTENER_INFERENCE 保持区分；主题卡不能证明制作事实，推荐歌曲仍须经过 MusicBrainz 核验。
- 原有深度分析护栏中只识别网页摘要、域名和正文的部分改为识别多种材料，不把“审核通过”当作本轮结论已获支持。

事实密集或存在冲突的回答由同一 Agent 条件式语义审校，检查归因、实体版本、支持程度和正文引用。Java 负责引用存在性、权限及有效版本的确定性校验，不冒充语义事实判断。未知引用直接拒绝；不能删除 ref 后原样保留无依据结论。

## 12. 多轮记忆、卡片与撤回

分析卡保存研究对象、版本范围、核心判断、Claims、证据 ID/版本、可公开快照、工作台版本、缺口和继承卡片 ID。短摘录快照遵守同一使用限制，不保存内部工具原文。

追问恢复完整研究上下文后，批量复核继承证据。旧摘要不能覆盖当前权威状态；证据撤回影响核心判断时，下一回答明确纠正。历史回答不静默改写，来源抽屉展示资料已更新/已撤回及必要说明。确需删除的内容同步清理证据快照、导出内容和缓存。

公开 SSE 延用现有耐久事件流，只报告已完成检索、有效证据数量、覆盖缺口和结果。不得输出隐藏思维链、系统提示、密钥及未经清洗的资料原文。

## 13. 前端与维护权限

用户端扩展既有分析/推荐卡：点击正文引用展开来源标题、发布者、材料类型、日期、定位和允许的短摘录；标明归因观点、主题解释、部分支持、冲突及失效状态。用户不需要理解向量分数、索引代次或内部审核 ID。

维护端提供资料登记、文件/URL 导入、批次结果、候选编辑、实体绑定、摘要与材料对照审核、发布/撤回、版本历史、索引任务和重试、检索测试、重建/切换/回退及审计查询。管理界面与受控命令调用同一 Java 业务契约，不能通过脚本直接绕过审核写正式 Milvus。

Java 服务端校验知识管理角色；普通注册账户没有管理权限。修改操作沿用 Session/CSRF 防护。Python 只能持服务身份使用指定内部接口，不能伪造审核人或发布操作。

## 15. 性能、缓存与运行维护

- 热检索总预算建议默认 5 秒，可配置；并行通道共享截止时间，向量计算及回查均有独立超时。批量索引限流，避免抢占对话 CPU。
- 模型和客户端复用，启动后受控预热；模型未就绪时返回明确状态，不让用户请求触发反复下载。
- 查询向量缓存绑定模型代次、模板和标准化查询；候选 ID 可短期缓存，但每次返回仍执行权威回查。
- 发布、更新和撤回推进知识修订号以失效候选缓存。不得用可绕过撤回的“有效证据长期缓存”。
- 区分服务存活、知识检索就绪、索引就绪；Milvus 不应成为普通对话启动的强制依赖。
- 固定并验证 Milvus、MinIO、etcd 和 SDK 组合，提供独立知识库启动配置，重新确认本地镜像可用性；不默认为当前本机已经可用。
- Windows 下载、工具、模型和缓存优先 E 盘，选择位置前检查已有目录及空间。长期模型保留在明确持久目录/volume；成功验证后清理安装包及可安全清理的临时内容。
- 备份 MySQL 权威数据、审核记录、允许保留的摘录和索引配置。Milvus 可从权威数据重建；恢复后默认关闭对外知识检索，先对账、验证引用和权限再开放。

观测包括检索状态/通道耗时、模型就绪、回查剔除原因、覆盖不足、任务积压/死信、索引差异、撤回传播、引用支持状态和端到端延迟。链路关联 conversationId / runId / jobId，日志脱敏，不记录凭据或整篇输入材料。

## 16. 完整验收与质量目标

建设固定语料版本和至少 50 个初始问题，保留开发集与独立验收集，记录问题对应的实体、相关知识版本、答案材料及不可支持的结论。具体资料规模以人工维护能力与覆盖质量决定，不把历史主题卡数量当作本次验收语料。

| 类别 | 必测情况 |
| --- | --- |
| 实体 | 同名、别名、中英文名称、作品/录音/发行、现场与重录版本 |
| 检索 | 精确事实、背景语义、主题查询、跨对象比较、库外问题 |
| 支持关系 | 相关但不支持、观点归因、部分支持、冲突、转载同源 |
| 一致性 | 重复/乱序任务、旧版本 UPSERT/DELETE、撤回、来源失效、生成中状态变化 |
| 故障 | Milvus、模型、Java 回查、队列、Worker 租约与回报失败 |
| 多轮 | 继承对象和 Claims、追问检索、旧证据更新、撤回后的纠正 |
| 权限 | 普通用户不能管理，未发布资料不可读取，内部身份隔离和 CSRF |
| 输入安全 | 非法 URL/重定向、资料指令注入、超长文件、受限内容和短摘录边界 |
| 运维 | 幂等导入、备份恢复、全量重建、增量追平、代次切换与回退 |
| 扩展边界 | 当前只启用人工输入，预留自动来源不可越过候选/审核权限 |

拟定质量门槛：

- 未知引用、错误实体/版本、重新使用已撤回材料及越权读取，任一出现即不通过。
- 重复、乱序和撤回用例全部通过；故障不得破坏原有普通推荐主链路。
- 有标注答案的独立检索集 Recall@10 目标不低于 90%，同时报告 MRR、对象覆盖和无匹配处理。
- 人工核对的事实引用支持率目标不低于 95%，必须同时统计引用覆盖，防止只给少量容易支持的事实来抬高分数。
- 库外与不支持用例不得用不相关命中编造答案；冲突必须保留或明确解释。
- 分别报告冷启动、热检索及端到端 P50/P95，不以检索速度替代回答质量；容量和并发随部署资源记录。

使用相同问题比较启用/关闭 RAG 的支持率、完整性、无答案处理、延迟和外部调用量，确认知识确实改善回答。自动检查负责结构、引用和状态约束；语义事实与深度由材料对照人工核验，不能把链接存在冒充正确。
