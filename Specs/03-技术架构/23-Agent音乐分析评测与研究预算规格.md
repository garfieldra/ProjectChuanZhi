# 音乐分析 Agent 评测与研究预算规格

## 目标

用可重复的真实问题检查统一 Agent 的音乐分析、追问、证据边界和运行时间。评测不规定工具调用顺序，也不把回答长度当作质量代理指标。每次修改研究策略前保存基线，修改后以相同问题、相同模型和尽可能相同的外部服务配置复跑。

## 用例与结果

- 用例覆盖描述性单曲分析、创作背景、作品/版本比较、证据不足、同名歧义、上一轮分析追问和普通推荐边界。
- 每个用例记录用户消息、预期结果类型、关键实体、事实密集程度，以及是否需要继承上一轮分析卡。
- 运行器通过公开 Java API 创建独立访客会话，发送消息，等待持久化 Agent Run 终态，读取公开回答与卡片；不读取模型隐藏思维链。
- JSON 结果保存公开回答、卡片、终态、耗时、工具动作摘要、来源数、Claims 状态和必要的错误码。报告中不存 Cookie、密码、API Key 或内部服务 Token。

## 自动检查

- 硬约束：运行成功、回答非空、预期卡片出现、引用指向卡片中的真实来源、非 unsupported 的事实 Claim 有证据、追问沿用原研究对象。
- 可比较指标：端到端耗时、搜索次数、页面精读次数、独立来源数、事实 Claim 支持率、答非所问率、失败率、模型/工具用量（若运行时提供）。
- 回答深度、论证具体性和事实准确性需要独立模型评审或人工抽查。自动结构检查不能冒充事实核验；评审必须看到问题、回答和引用的公开材料，并输出理由与不确定性。
- 基线比较按用例展示变化。外部网页会变化，因此时间和来源数量属于观察指标，不单独作为失败判定。

## 研究预算

- Agent 根据问题复杂度和证据缺口自主决定搜索、精读、换来源或停止。预算仅设置上限、单工具超时和无收益循环阻断。
- 描述性问题在已有足够证据时尽早作答；涉及创作背景、制作署名、版本差异的事实问题允许更高预算。
- 记录每一步是否增加了可用证据；连续两步没有新证据时停止该研究方向并说明边界。不得以固定“搜索几次”取代证据充分性判断。
- 先建立评测基线，再按失败用例调整预算。改动需要同时观察质量、P95 延迟和成本，不能单独追求更短耗时。

## 首轮验收

1. 评测命令可在无任何正式用户数据的情况下创建自己的测试会话并生成机器可读报告。
2. 至少包含单曲、事实背景、比较、追问和资料不足场景。
3. 失败用例可定位到运行状态、来源/Claim 检查或结果类型；基线报告可与新报告比较。
4. 研究预算的任何调整都以首轮基线和复测数据说明收益与退化。
